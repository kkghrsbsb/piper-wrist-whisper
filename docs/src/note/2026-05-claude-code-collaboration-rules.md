# Claude Code 协作规则(草稿)

> 这是个人对当前项目下与 Claude Code 协作的方法论沉淀。
> 不是设计基线,会随实践调整。**所有规则的目的:让自己保持对系统的 mental model,不把架构决策让渡给 AI。**

---

## 核心定位

把 Claude Code 当**实习生**,不是当**工程师**。

- 实习生的工作模式:你给它一个**很小的、有明确验收标准的任务**;它做完;你检查;你给反馈;**你**在脑子里维护整个项目的 mental model
- 工程师的工作模式:自主规划、连贯推进、跨任务记忆——**这种模式当前不开放**

---

## 任务粒度规则

- **每次只让 Claude Code 实现一个节点或一个组件**,不能一次让它"实现 Phase 1 全部内容"
- **单次任务的代码改动应在 200 行以内**(经验值,可调)
- **任务完成后人工验证**:你跑一次,确认能跑、风格符合预期,再决定下一步
- **不让 Claude Code 主动决定下一步做什么**——下一步永远由人工指定

---

## 信息边界

Claude Code 拿到的上下文:

- 仓库当前文件
- `docs/src/` 下你给它读的具体文档
- 本次任务的明确 prompt

Claude Code **不应该自己推断**:

- 仓库历史进度(已经做过什么)→ **由你在 prompt 里告诉它**
- 下一步该做什么 → **由你在 prompt 里指定**
- 文档之间的依赖关系 → **由你引导它读哪份**

如果它读完文档后问出"我应该从哪个 Phase 开始"这种问题,说明边界没设好——文档不该让它产生"自主选择起点"的错觉。

---

## 协作铁律

以下规则在每次交互中适用,在 prompt 顶部直接粘贴:

1. **改动范围明确**:每次只实现一个节点或一个组件
2. **接口先写测试**:rule-matcher、input-router、mode-router 等纯逻辑节点,先写 pytest,再实现到测试通过
3. **远程 LLM 调用要 mock**:llm-client 单元测试用 httpx mock,不要真打远程
4. **真机 vs 仿真**:涉及 dora-piper 的代码,先在仿真验证再上真机
5. **预设动作轨迹不由代码生成**:所有 npz 必须 teach mode 录制
6. **不要主动引入新依赖**:Redux/Zustand/asyncio 等,如果文档没要求就别加
7. **不修改已有 `rerun-*` 节点**:除非任务明确说"修改这个节点",否则视为只读
8. **WebSocket 协议是契约**:前后端共同遵守 plan 文档中的 schema,改动需双向同步
9. **不在 README.md 写实现细节**:CLAUDE.md 已经定了 README 只放概览;实现细节进对应 skill 目录

---

## 不要做的反模式

❌ "请按这份文档实现整个项目"
→ 它会铺出 30 个空文件,每个里面塞个 TODO,看着热闹但什么都不能跑

❌ "先搭一下基础骨架"
→ "基础骨架"对它来说边界太宽,会自由发挥

❌ "你觉得应该从哪开始?"
→ 它会给一个合理但非最优的建议;让渡架构决策权

❌ 不读它的复述就直接让它写代码
→ 它可能误解了某个关键设计,代码地基歪掉

## 第一次任务模板

仓库已经有 plan / adr / learn 文档时,第一次让 Claude Code 动手前先做"理解校对":

```
我已经把项目文档放在 docs/src/。请你做三件事,按顺序:

1. 通读以下三份文档,然后用你自己的话给我一份 200-400 字的项目理解,
   覆盖:核心目标、双模式区别、节点架构、当前已有节点。
   - docs/src/README.md
   - docs/src/adr/2026-05-001-dual-mode-llm-vlm-architecture.md
   - docs/src/plan/2026-05-system-architecture-baseline-plan.md
   不要复制原文,要复述。

2. 列出在阅读中发现的、需要在动手前澄清的关键问题(不超过 3 个)。
   只列影响实现的,不列锦上添花的。

3. 暂时不要写任何代码、不要创建任何文件。

如果发现文档里有任何与你常识冲突、或技术上不可行、或明显矛盾的地方,
请在第 2 条里指出,而不是自己默默改设计。

我会根据你的复述和问题确认理解到位了,再让你开始具体工作。
```

## 已经踩过的坑

- **文档与仓库实际状态脱节**:第一版指导文档里假设的目录结构(`piper-voice-stack/`)与实际仓库名(`piper-wrist-whisper`)、节点命名风格(下划线 vs 连字符)不一致,导致 Claude Code 第一次读完后提出三个澄清问题。教训:文档要反映**当前事实**,不要超前规划目录细节。

- **一份文档承载太多内容**:第一版把架构图、节点接口、状态机、Phase、协作规则都塞进一份文档,导致每次微调一个 Phase 就要重写整份。改进:按 my-skills 工作流拆成 plan / adr / learn / notes,各自单一目的。
